## 1. Product Vision

A **multi-tenant SaaS HRMS** for small-to-mid-size companies (10–5,000 employees). The single biggest differentiator versus building a one-off internal tool: **nothing is hardcoded per company**. Every organization that signs up gets its own isolated space, and a Super Admin (Anthropic-style "platform operator," not a company employee) provisions tenants. Within each tenant, an Org Admin configures everything — roles, permissions, modules visible, approval workflows, leave policies, org structure — without any developer touching code post-deployment.

Design principle to repeat throughout the build: **"Configuration over code."** Anything that could plausibly differ between two customer companies (leave types, approval chains, salary structure, designations, holiday calendars, document templates) must live in the database as tenant-scoped configuration, not in application logic.

### Target audience mindset (10–5,000 employees)
- Not enterprise-only (no SAP-level complexity expected day one), but must not feel like a toy — HR admins expect Workday/Zoho People/Darwinbox-level polish.
- Buyers are typically HR/Ops leads and founders, not IT departments — onboarding and self-serve setup must be simple (Excel upload, guided setup wizard), not "call our implementation team."
- Must support hybrid work reality (in-office/remote/WFH is a first-class concept, not an afterthought).
- Price-sensitive → multi-tenant shared infrastructure (not one deployment per customer) is the right default, with the option to consider dedicated tenancy for very large customers later.

## 2. Tech Stack

**Backend**
- FastAPI (Python 3.12+), Pydantic v2 for schemas
- PostgreSQL (primary datastore) with SQLAlchemy 2.x (async) + Alembic for migrations
- Redis (caching, rate limiting, Celery broker, session/blacklist for JWT)
- Celery (or Arq) for async jobs: bulk Excel import, email/notification sending, offer-letter/PDF generation, payroll runs, report generation
- JWT-based auth (access + refresh tokens), with tenant context embedded in claims
- Object storage: S3-compatible (AWS S3 / MinIO for self-host) for documents, offer letters, profile photos, Excel uploads
- Search: PostgreSQL full-text initially; consider OpenSearch later if employee/document search grows

**Frontend**
- React 18+ with TypeScript
- Vite as build tool
- TanStack Query (React Query) for server state
- Zustand or Redux Toolkit for lightweight client state (prefer Zustand — less boilerplate)
- React Router v6
- Tailwind CSS + a component library foundation (shadcn/ui recommended — copy-in components, not a black-box dependency, which matters since design will need to flex per tenant branding)
- React Hook Form + Zod for form handling/validation (share validation logic shape with backend Pydantic where practical)
- Recharts or Nivo for dashboard visualizations
- react-pdf or server-side PDF generation (see below) for offer letters/payslips

**Cross-cutting**
- OpenAPI schema auto-generated by FastAPI → generate a typed TS client for the frontend (e.g. `openapi-typescript` + `openapi-fetch`) so frontend/backend never drift.
- Docker + docker-compose for local dev.
- Structured logging (JSON logs) with request-id + tenant-id correlation from day one.

## 3. Multi-Tenancy Architecture

### 3.1 Isolation model — recommended approach
Use **shared database, shared schema, with `tenant_id` on every tenant-scoped table**, enforced via PostgreSQL **Row-Level Security (RLS)**, not just application-level filtering.

Implementation detail:
- Every tenant-scoped table has a `tenant_id UUID NOT NULL REFERENCES tenants(id)` column, indexed, and included as the leading column in composite indexes for high-traffic queries.
- A Postgres session variable (`SET app.current_tenant_id = '<uuid>'`) is set at the start of every request (via a FastAPI dependency/middleware after auth resolves the tenant from the JWT), and RLS policies reference `current_setting('app.current_tenant_id')`.
- The Super Admin's platform-level tables (tenants, subscription/billing, platform admins) are **not** tenant-scoped and live outside RLS.
- Never trust `tenant_id` from the request body/query params for writes — always derive it from the authenticated session.

### 3.2 Tenant provisioning flow
1. Super Admin creates a tenant (company name, subdomain/slug, plan, initial admin email).
2. System auto-creates: tenant record, default role set, and sends an invite to the initial Org Admin.
3. Org Admin completes a **Setup Wizard**: company profile, working days/holiday calendar, departments, designations, leave policy defaults, branding, and bulk employee import.
4. Tenant is "active" only once minimum setup is complete.

### 3.3 Tenant identification
- Subdomain (`acme.yourhrms.com`) or path-based fallback (`app.yourhrms.com/acme`).
- Custom domain mapping (`hrms.acmecorp.com`) is Phase 2 — note in schema (`tenants.custom_domain`).

## 4. Roles, Permissions & Access Control (RBAC)

### 4.1 Model
- `permissions` (platform-defined, seeded, immutable via UI) — atomic capabilities, e.g. `leave.apply`, `leave.approve`, `employee.view.own`, `employee.view.team`, `employee.view.all`.
- `roles` (tenant-scoped, admin-creatable) — named bundle of permissions.
- `role_permissions` — many-to-many.
- `user_roles` — many-to-many.
- **Scope matters:** `own`, `team`, `department`, `all`.
- Module visibility is permission-driven.

### 4.2 Enforcement
- Backend: `require_permission("leave.approve")` dependency on every endpoint.
- Frontend: `usePermission("leave.approve")` hook / `<Can permission="..." />` wrapper.
- Cache resolved permission set per user per session in Redis.

### 4.3 Default roles per new tenant
`Org Admin`, `HR Admin`, `HR Executive`, `Reporting Manager`, `Finance Admin`, `Employee`.
